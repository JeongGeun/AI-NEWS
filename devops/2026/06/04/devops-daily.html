6. AI 에이전트의 MCP 서버, CTEM 공격 표면 맵에서 누락된 보안 사각지대

출처: Dev.to DevOps · 중요도: 높음

한국어 요약: 현재의 CTEM(Continuous Threat Exposure Management) 프로그램은 엔드포인트, ID, 클라우드 구성 등은 파악하지만 AI 에이전트가 사용하는 MCP(Model Context Protocol) 서버는 감지하지 못한다. MCP 서버는 AI 에이전트가 시스템에 접근하는 경로로, 기존 SAST 파이프라인이나 CSPM 도구가 인식하지 못하는 새로운 공격 표면이다. 독성 의존성, 노출된 자격증명, 과도한 권한 부여 등 기존 위험과 동일한 실패 모드를 가지지만 현재 보안 도구로 커버되지 않는다.

English Summary: Current CTEM programs fail to map MCP (Model Context Protocol) servers used by AI agents, creating a security blind spot. MCP servers—which enable AI agents to access systems, read data, and call APIs—represent a second attack surface that existing SAST and CSPM tools cannot enumerate. The vulnerability stems from familiar risk patterns (poisoned dependencies, exposed credentials, privilege escalation) but on an unmonitored layer.

핵심 키워드: MCP (Model Context Protocol), CTEM (Continuous Threat Exposure Management), SAST pipeline, CSPM (Cloud Security Posture Management), AI agents

7. SPF 10회 DNS 조회 제한: 이메일 인증 실패 원인

출처: Dev.to DevOps · 중요도: 보통

한국어 요약: SPF 레코드는 DNS 조회를 유발하는 메커니즘을 최대 10개까지만 허용하며, 이를 초과하면 PermError 오류가 발생한다. include: 메커니즘은 재귀적으로 작동하여 SaaS 스택에서 4-5개의 상위 include만으로도 한계에 도달할 수 있다. 이 문제를 해결하려면 include: 항목을 IP 주소 범위(ip4:/ip6:)로 교체해야 한다.

English Summary: SPF records have a hard 10 DNS-lookup limit per record, and exceeding it triggers a PermError. The include: mechanism counts recursively, meaning a SaaS stack with just 4-5 includes can hit the limit. The fix is to replace include: entries with their resolved IP ranges (ip4:/ip6:), which don’t count toward the lookup limit.

핵심 키워드: SPF, DNS, PermError, SendGrid, Google, Mailgun, InboxGreen

8. 모니터링과 관찰성의 차이: 대시보드는 녹색인데 서비스는 죽어있다

출처: Dev.to DevOps · 중요도: 보통

한국어 요약: 저자는 모든 메트릭이 정상을 나타내는 대시보드를 보며도 실제 사용자가 5초 응답 지연을 겪는 경험을 했습니다. 이를 통해 모니터링과 관찰성(Observability)의 근본적인 차이를 깨달았는데, 모니터링은 ‘문제가 있는가?’를 묻지만 관찰성은 ‘왜 문제가 생겼는가?’를 답할 수 있어야 한다고 설명합니다. 차별화되지 않은 지표 수집은 실제 사용자 경험을 반영하지 못하므로 진정한 관찰성 체계 구축의 필요성을 강조합니다.

English Summary: The author discovered that a perfectly green monitoring dashboard masked real user problems (5-second checkout delays caused by third-party API timeouts). He distinguishes between monitoring (asking “is it broken?”) and observability (asking “why is it broken?”), arguing that most teams build decorative telemetry rather than systems that enable root cause analysis without code changes.

핵심 키워드: monitoring systems, observability, dashboard metrics, SRE practices
